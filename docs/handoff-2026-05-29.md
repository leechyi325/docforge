# DocForge 交接总结

日期：2026-05-29

## 当前状态

DocForge 当前已具备可分发桌面包的基础能力：Tauri 桌面应用通过 sidecar 调用 PyInstaller 打包后的 Python 引擎，并把 Pandoc 作为独立 sidecar 随应用一起分发。macOS 本地已成功构建 `.dmg`，Windows 已提供 PowerShell 构建脚本，但需要在 Windows 环境执行。

当前推荐处理链路：

```text
Markdown 或 .docx 输入
  -> Tauri 桌面端收集参数
  -> Rust 调用 docforge-engine sidecar
  -> Python engine.cli format
  -> Markdown 输入时调用 Pandoc sidecar 转为基础 .docx
  -> python-docx 本地确定性格式整理
  -> 格式诊断
  -> 桌面端显示结果与进度日志
```

Python 引擎仍是业务源头。React 和 Rust 只做参数收集、子进程调用、进度转发和状态展示，不应重新实现格式整理、诊断、模型 provider 或修复逻辑。

## 已交付能力

- Markdown 输入通过随应用打包的 Pandoc sidecar 转换为 `.docx`。
- `.docx` 输入可直接格式整理并输出新的 `.docx`。
- `.doc` 老格式会被明确拒绝。
- 当前 profile 已收敛为 `default` 和 `general`：
  - `default`：默认文稿模板，包含日期和部门字段。
  - `general`：通用格式文档，沿用默认模板主体样式，但不包含日期和部门字段。
- Python 引擎已支持 PyInstaller frozen 环境下加载内置 YAML profile。
- Python 引擎已支持通过 `DOCFORGE_PANDOC` 指定 Pandoc 可执行文件路径。
- macOS 打包流程已打通：PyInstaller engine sidecar + Pandoc sidecar + Tauri `.dmg`。
- Windows 构建脚本已提供：`scripts/build-engine.ps1`、`scripts/fetch-pandoc.ps1`、`scripts/build-desktop.ps1`、`scripts/setup-dev.ps1`。
- Tauri v2 使用 `tauri-plugin-shell` 调用 sidecar，不再在打包应用里搜索系统 Python。
- 桌面端 API Key 仍通过环境变量传给子进程，不进入 CLI argv。

## 关键修复：PyInstaller + python-docx

测试打包应用时曾出现：

```text
engine process exited with status Some(1)
[Errno 2] No such file or directory: '.../_MEI.../docx/parts/../templates/default-footer.xml'
```

原因是 python-docx 在运行时用 `__file__` 相对路径查找 `docx/templates/*.xml`，但 PyInstaller `--onefile` frozen 环境不会把包内 `.py` 文件以普通路径形式展开，导致 `docx/parts/../templates/...` 解析失败。

修复方式：

- `engine/engine.spec` 使用 `collect_data_files('docx')` 打包 python-docx 模板数据。
- `engine/runtime_hook_docx.py` 在 frozen 环境下把 python-docx 的模板路径解析 patch 到 `sys._MEIPASS/docx/templates`。
- 重新构建后的 `docforge-engine` 已通过 Markdown→docx 和 docx→docx 手工验证。

## 打包流程

macOS 完整打包：

```bash
scripts/build-desktop.sh
```

该脚本会：

1. 准备 `.venv` 和桌面端依赖。
2. 下载 Pandoc sidecar 到 `apps/desktop/src-tauri/binaries/`。
3. 用 PyInstaller 构建 `docforge-engine-{target_triple}`。
4. 执行 `npm run tauri build` 生成 `.app` 和 `.dmg`。

macOS 输出位置：

```text
apps/desktop/src-tauri/target/release/bundle/dmg/DocForge_0.1.0_aarch64.dmg
```

Windows 完整打包需要在 Windows 环境执行：

```powershell
scripts\build-desktop.ps1
```

不要从 macOS 交叉编译 Windows 桌面包；PyInstaller sidecar 和 Tauri bundle 都应在目标平台构建。

## 开发运行

Python 环境：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e ".[dev]"
```

桌面端开发启动：

```bash
scripts/fetch-pandoc.sh
scripts/build-engine.sh
cd apps/desktop
npm install
npm run tauri dev
```

`npm run dev` 只启动 Vite/browser UI，不能调用 Rust/Python 后端。真实文档处理必须通过 `npm run tauri dev` 或打包应用验证。

## 关键文件

- `engine/engine.spec`：PyInstaller 打包规格，包含 profile YAML、python-docx 数据文件和 runtime hook。
- `engine/runtime_hook_docx.py`：PyInstaller frozen 环境下 python-docx 模板路径修复。
- `engine/profiles/loader.py`：frozen 环境下从 `sys._MEIPASS/engine/profiles` 加载 profile。
- `engine/converters/pandoc.py`：优先使用 `DOCFORGE_PANDOC`，再回退 `PATH` 中的 Pandoc。
- `apps/desktop/src-tauri/src/main.rs`：Tauri sidecar 调用、环境变量传递、进度事件转发。
- `apps/desktop/src-tauri/tauri.conf.json`：声明 `docforge-engine` 和 `pandoc` externalBin。
- `scripts/build-desktop.sh` / `scripts/build-desktop.ps1`：完整桌面端构建入口。
- `scripts/build-engine.sh` / `scripts/build-engine.ps1`：PyInstaller engine sidecar 构建。
- `scripts/fetch-pandoc.sh` / `scripts/fetch-pandoc.ps1`：下载并重命名 Pandoc sidecar。
- `scripts/setup-dev.sh` / `scripts/setup-dev.ps1`：创建开发用 sidecar 占位文件，避免 `cargo check` 因缺少 externalBin 失败。

## 已知限制

- 不支持 `.doc` 老格式。
- 不支持在线 Word 级预览。
- 不支持 Word/WPS 插件。
- 不支持正文润色、扩写或改写。
- 直接整理 `.docx` 时，输出路径必须和输入路径不同。
- 表格、页眉、页脚、批注、脚注、修订痕迹等复杂 Word 区域还不是一等格式整理对象。
- 默认 profile 的日期/部门字段识别仍偏位置规则，后续需要更可靠的结构识别策略。
- Windows 打包脚本尚未在 Windows 机器上实际验证。
- macOS 包当前未做正式开发者签名和 notarization，分发给其他机器时可能触发 Gatekeeper 提示。

## 建议下一步

- 在 Windows 环境执行 `scripts\build-desktop.ps1`，验证 `.exe` / installer 输出。
- 给默认 profile 增加更可靠的日期/部门识别逻辑，避免固定段落位置误判。
- 增加“AI 智能识别”文档类型/入口，用 LLM 辅助结构识别，但最终格式动作仍走本地确定性代码。
- 增加打包后的手工 QA 清单，覆盖 Markdown、`.docx`、本地 provider、远程 provider、无 Pandoc/无 API Key 等场景。
- 规划 macOS 签名/notarization 和 Windows 代码签名流程。
